## 业务架构

申请-审批流程：
1. 用户前端发起场地申请单，后端进行申请单、附件、时间表的存储；
2. 具权用户前端发起场地申请单列出请求，后端分析场地下属所有申请单，将内容、附件、时间表提交给前端
3. 前端分析冲突，高亮显示，进行审批，返回结果与评论（comment/可选）
4. 若拒绝申请单，则后端直接将对应审批标记为拒绝，并对关连用户发送站内信；若通过申请单，则返回的结果中包含“known_confict” []string 组，表示前端已知冲突的 application_id 列表。若前端已知冲突与后端统计的冲突吻合，则后端通过目标审批，同时自动拒绝冲突审批（请使用“事务”确保多个数据条目修改的原子性）、发送站内信；若前端已知冲突与后端统计的冲突不吻合，则后端返回冲突的 application_id 供前端刷新显示，不更新任何审批的状态。

时间表存储逻辑：申请单本体与时间表的存储是分离的。当申请单发出后，会在时间表注册时间区段，同时通过 application_id 字段与申请单建立联系。时间表的状态（“status”字段）已弃用（你可以移除它），请使用联表（JOIN）的方式通过 application_id 获取其字段 application_status 进行筛选。

附件存储逻辑：申请单本体与附件存储分离，附件统一存储于 attachments 表中，申请单本体通过 has_attachments 字段是否进行附件表查询。

申请单 activity_coordinator 字段：这是一个 JSON 字段，在当前版本不使用，存储与解析的部分请**预留**以供后期迭代。

站内信：当前版本不构建，预留调用即可。

维护申请单：一类特殊的申请单，用于占用场地时间用于维护。这类申请单由特定用户发起且无需审批。当前版本不构建，仅在“状态”字段的枚举中预留即可。

### 通用 JSON 模型 (JSON OBJECT)

TIMETABLE 模型：

- []object
    - begin string
    - end   string

APPLICATION 模型：
- application_type string 固定值“normal”，预留后期使用
- time_request []object TIMETABLE模型
- estimated_participants int (可选) 预估人数
- description string (可选)
- attachments []object (可选) ATTACHMENT 模型
- activity_name (可选) string
- activity_organizer (可选) string
- activity_coordinator (可选) []object 预留

COMMENT 模型：
- id int 回复帖ID
- text string 回复文字内容
- attachments []object (可选) ATTACHMENT 模型

ATTACHMENT 模型：
- index int 该附件的在附件列表的索引位置
- file_token string 文件令牌
- file_type string 文件类型
- file_name string 文件显示名称

### 新建申请单

API：POST /api/venue/{venue_id}/application

API 功能：创建对于某个场地的申请申请单

API 权限：需要具有该场地的 reserve 权限或 AllVenueReservation 系统权限

API 链路：接受前端表单-svc层校验合法性-数据库存储

API 表单：APPLICATION 模型

API 成功响应：
- application_id int

说明：申请单本身、时间表、附件应该储存在三个表中，请参阅工作区代码。

### 删除申请单

API：DELETE /api/application/{application_id}

API 功能：软删除创建的场地申请申请单

API 权限：申请单创建者（applicant_uid）或具有对应场地 Manage 权限或具有 AllVenueManage 系统权限

API 链路：接受前端表单-svc层校验合法性-数据库更新

API 表单：无

API 成功响应：无

说明：如果申请单被软删除，则同步软删除附属的 timetable 项和 attachment 注册；

### 请求申请单

API：
- GET /api/venue/{venue_id}/application 获取场地下属申请单
- GET /api/user/application 获取用户（自身）发起的所有申请单

API 功能：获取申请单（列表）

API 权限：
- 获取场地下属申请单：需要对应场地的 reserve 权限或 AllVenueReservation 系统权限
- 获取用户（自身）发起的申请单：无特殊权限

API 链路：接受前端表单-svc层校验合法性-数据库查询并返回

API 表单：无

API 成功响应：
- []object
    - id int 申请单 application_id
    - ... (muti) APPLICATION 模型所含字段
    - comments []object COMMENT 模型

### 审批申请单

API：PUT /api/application/{application_id}

API 功能：提交申请单审批结果

API 权限：具有对应场地 Approval 权限或具有 AllVenueApproval 系统权限

API 链路：接受前端表单-svc层校验合法性-数据库更新

API 表单：
- decision string 审批结论，可以为 rejected/approved
- comment object (可选) COMMENT 模型，审批意见
- known_conflicts []int 前端已承认冲突的 application_id（仅当 decision=approved 时具有该字段）

API 成功响应：无

冲突检测响应：
- new_conflicts []string 未被前端 known_conflicts 包括的冲突申请单 id

业务说明：参见“申请-审批流程-4”；“冲突”定义为：同一 venue_id 下，任何两个申请单的 timetable 存在交集。
