## 总体要求

### 总目标

工作区代码为一个场地管理系统的 go 后端，请你现在实现场地管理的增删改查部分，包括与前端对接的 Controller 层及其 DTO 模型、业务层逻辑及其 Model 模型、数据访问层及其 Entity 模型。我会详细告知你各部分模型的具体要求与逻辑框架，同时请你参考已有的 sql 文件与 Model 文件。

### 代码规范

#### 模型转换

Repository 依赖于 Domain，负责 Models 和 Entity 的互相转换

Presentation 依赖于 Domain，由 Controller 负责 DTO 向 Models 的单向转换

#### 错误处理

表现层的统一 API 错误与业务层错误分离，在 Controller 中实现转换。

表现层错误：统一定义在 utils-apiException 中，通过 errorHandler 中间件实现统一错误处理与转换成 JSON 格式返回。

业务层错误：哨兵错误统一定义在对应业务包中的 exceptions.go 中，以便外部通过 errors.Is() 进行错误类型判断。如果需要传递来自数据访问层等的错误，可以使用多重错误包装的方式向外传递。

业务层错误到表现层错误为多对一关系，避免过多的信息泄露给外部。在表现层的转换中，原始业务层错误可以通过 apiException.AbortWithException 方法的第三个参数传递给 errorHandler，通过日志打印。

## 业务架构

场地的权限管理逻辑为：单独一表记录权限组具体权限，每个用户分配一个权限组，决定用户可否进行场地有关操作。

场地的位置分类逻辑为：各场地有其所属的 building（楼区），通过 location_building_id 字段记录；各楼区有其所属的 campus（校区），通过 location_campus_id 记录（请参阅venue_buildings.sql）；前端会首先请求楼区列表，包含楼区的显示名称等，而后与后端的数据交换全部通过id进行。

## 详细要求

### 新建场地

API：PUT api/venue

API 功能：创建一个新的场地

API 权限：需要具有 CreateNewVenue 系统权限

API 链路：接受前端表单-svc层校验合法性-数据库存储

API 表单：
- name string
- building_id int
- type_id int (可选)
- description string (可选)
- cover_image_token string (可选)
- images_token []string (可选)
- capacity (可选)

API 成功返回表单：
- venue_id int

### 修改场地

API：PUT api/venue/{venue_id}

API 功能：修改一个已有场地的场地信息

API 权限：需要具有对应场地的 Edit 权限或者 AllVenueEdit 系统权限

API 链路：接受前端表单-svc层校验合法性-svc层更新既有模型-数据库更新

API 表单：等同“新建场地”接口，但所有字段均可选，只更新前端回传的字段

### 删除场地

API：DELETE api/venue/{venue_id}

API 功能：删除一个已有场地

API 权限：需要具有对应场地的 Edit 权限或者 AllVenueEdit 系统权限

API 链路：接受前端表单-svc合法性判断-数据库删除操作

API 表单：无

### 列出场地

API：GET /api/venue

API 功能：列出用户可访问的所有场地

API 权限：需要具有对应场地四种权限中的任意权限，或者对应系统四种权限中的任意权限

API 链路：接受前端表单-svc层进行查询建构-数据库查询

API 表单：
- b []int (Query/可选) :筛选位于特定楼区（building_id）的场地
- t []int (Query/可选) :筛选具有特定标签（type_id）的场地
- p []string (Query/可选) :筛选用户具有特定权限的场地，值可以为R/A/M/E的任意组合，对应四种场地权限
- s string (Query/可选) :搜索关键词
- o int (Query/可选) :分页偏移（offset）
- n int (Query/可选) :单页最大（pagesize），无此项默认 12

API 成功返回表单：
- []object
    - venue_id int
    - name int
    - building_id int
    - type_id int
    - description_text string
    - cover_image_token string
    - permission []string
    - attachments []object
        - type string
        - index int
        - file_token string
    - timetable []object
        - start string
        - end string
        - status string

业务逻辑：

前端的“场地预约”页面与“场地审批”页面均调用此接口，区别仅仅为 p 筛选器字段。
例如（所有ID均为虚构）：
- 查询“教学楼和体育馆所有可预约的会议室场地”的调用可能为：GET /api/venue?b=13,17&t=7&p=R
- 查询“关键词为‘物理’的所有教学楼我可审批的实验室场地”的调用可能为：GET /api/venue?b=13&t=8&p=A&s="物理"

attachments 字段从 attachments 表查询 biz_type=“venue” biz_id=<venue_id> 的条目。

timetable 字段从 venue_timeslots 表查询，为未来的场地占用情况。距今超过7日的占用信息不予返回。最多返回32条占用信息。

### 列出楼区与校区信息

API：GET api/venue/locations

API 功能：提供楼区与校区信息，以便前端进行显示

API 权限：需要具有楼区包含的任意场地的场地四种权限中的任意权限，或者对应系统四种权限中的任意权限

API 链路：接受前端表单-查询用户VAGID对应可用场地-查询用户可用场地对应的楼区-查询楼区信息-查询校区信息并返回

API 表单：无

API 成功返回表单：
- []object
    - building_id int
    - building_name string
    - location_campus_id int
- []object
    - campus_id int
    - campus_name string

业务逻辑：

登录的用户可直接从上下文取得 VAGID，去 venue_accesses 表查询可得用户有权访问（四种权限任）的场地，去 venues 表使用高级SQL查询可得对应的楼区ID列表，在 venue_buildings 查询获得楼区信息并返回为第一个对象列表，对所有提及的 location_campus_id 在 venue_campuses 查询获得校区信息并返回作为第二个对象列表。

为了避免三次SQL查询，你可以使用JOIN方法来节省查询次数。
