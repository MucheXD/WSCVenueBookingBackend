如你所见，现行场地有一个比较完整的控制逻辑，但还没有管理相关的接口。你现在需要完成的就是场地权限管理的部分，具体而言：

我新建了一个 venue_role.sql 表，这建立了 vagid 与显示名称的对应。现在，完成以下 API 链路：

### 列出场地权限角色组

API：GET /api/access
需要权限：ChangeUserVenueAccess 系统权限
返回表单：
- []object
    - vagid int
    - name string
    - description string

### 修改用户场地权限

无需新建链路，请在“管理员更新任意用户信息”的链路基础上修改

### 新建场地权限

API：POST /api/access
需要权限：ChangeUserVenueAccess 系统权限
请求表单：
- name string
- description string
- []object
    - venue_id int
    - allow_reserve bool (缺省为 false)
    - allow_approval bool (缺省为 false)
    - allow_edit bool (缺省为 false)
    - allow_manage bool (缺省为 false)
返回表单：vagid int
业务逻辑：请求后，权限信息转换到 venue_accesses 表存储，角色元信息转换到 venue_roles 表存储。如果最终 row affect 不等于传入的组数，则回退数据库更新，返回业务错误。

### 列出可修改权限的场地

API：GET /api/venue/list
需要权限：ChangeUserVenueAccess 系统权限
返回表单：
- []object
    - venue_id int
    - name string
    - building_id int
    - type_id int
业务逻辑：返回全部场地列表即可。需要注意的是，这次数据库读操作不应该使用 /api/venue 链路的方法，因为那会同步请求所有相关的附件、时间表等，造成资源浪费。请参考 application 的做法，分成 GetFull... 和 Get...Body 两个业务层方法。
